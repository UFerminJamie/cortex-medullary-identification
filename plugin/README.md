# CorticalMedullaryIdentification for DSA

This is a Slicer CLI Web image, shown in HistomicsUI's Analyses panel. The image does only Girder staging, SSH submission/monitoring, and result publishing. TRIDENT and cuML run in a separate Slurm job on HiPerGator. The image does not request a Docker GPU or run inference in the DSA worker.

## Deployment prerequisites

1. Verify the Athena versions of Girder, HistomicsUI, `slicer_cli_web`, and Girder Worker, including that the worker imports Docker CLIs and passes `docker-params.volumes`. The code follows the [Slicer CLI Web resource and multiple input contract](https://github.com/girder/slicer_cli_web#docker-clis) and [HistomicsUI analysis integration](https://github.com/DigitalSlideArchive/HistomicsUI#annotations-and-metadata-from-jobs). This deployment could not be inspected from the local checkout.
2. On HiPerGator, install this repository and its `TRIDENT/` checkout in the existing `cort_med_gpu` environment. Record the TRIDENT commit. The launcher checks the batch runner's current flags and H5 overlap attributes at run time. The upstream `run_single_slide.py` currently accepts `--overlap` but fails to pass it to `extract_tissue_coords`; this plugin uses `run_batch_of_slides.py --task all` on a one-slide directory as the supported equivalent. This keeps segmentation, coordinates, and feature extraction in order.
3. Confirm an approved SSH route from the DSA worker host to a HiPerGator login host, a Slurm account/QOS with L4 allocation, and a writable project/scratch output root. The worker does **not** call `sbatch` locally. The remote project checkout must be readable on compute nodes. Do not configure this on a login host where UF policy prohibits the connection or transfer workload.
4. Provision a Girder service account with read access to the approved slide and model folders and write/annotation access only to the approved slide folders. Give it an API key with the needed scopes. Restrict use of this imported CLI to the DSA users/groups that already have annotation rights in those folders. Slicer CLI Web checks selected resource read access for the submitting user; the service account's folder allowlist limits where it can publish.
5. On the Docker daemon host used by Girder Worker, mount a directory at `/etc/cort-med-worker`. Place `config.json` there based on `config.example.json`, plus `girder-api-key`, `ssh-key`, and `known_hosts`. Make the directory and files readable only by the worker's UID 1000. Keep the key, API key, and private site configuration outside this repository and the image. `known_hosts` must contain the verified HiPerGator SSH host key; `StrictHostKeyChecking=yes` is enforced. The CLI image mounts this directory read-only at `/run/cort-med` using Slicer CLI Web's `docker-params.volumes`.
6. In `config.json`, set the HTTPS Girder API URL, SSH host/user, remote project and output roots, approved Slurm account/QOS, comma-separated allowed DSA folder IDs, and comma-separated SHA-256 digests of approved `.pkl` checkpoints. The model allowlist is required because pickle loading executes Python code. No model is loaded before its downloaded bytes match an approved digest. The config contains no credentials.
7. Build and push an image under your own Docker Hub namespace, then import its immutable tag in the Slicer CLI Web admin page's task folder. Do not use `latest` for deployment. The local Docker Desktop DSA instance is in use, so the repository work does not restart or reconfigure it.

```bash
docker build -f plugin/Dockerfile -t YOUR_NAMESPACE/cortical-medullary-identification:0.1.0 .
docker push YOUR_NAMESPACE/cortical-medullary-identification:0.1.0
```

The image reports `CorticalMedullaryIdentification` from `--list_cli` and returns its Slicer XML from `CorticalMedullaryIdentification --xml`. Importing the image creates the HistomicsUI Analyses entry with Reload, Submit, Jobs, IO, Additional Options and API config panels. The native DSA file chooser supports one or multiple Input Image files and shows its Item Filter (Regular Expression) matches before confirmation. Select the large-image source files, not a server path. The two `.pkl` selectors must refer to the **same** shared binary SVC file. Distinct class checkpoints are rejected until a validated calibration and score combination model is implemented.

## Processing and storage

The worker downloads approved Girder files into a temporary directory, verifies the model digest, stages them over SSH with verified host keys, and submits one Slurm job with `--gres=gpu:l4:1 --cpus-per-task=8 --mem=64G --time=24:00:00` on the `hpg-turin` partition. Slurm account and QOS come from the worker configuration. The original preprocessing launcher uses 32 GB and 12 hours; inference uses 64 GB and 24 hours. The combined sequential job uses the inference ceiling. Check allocation availability with HiPerGator before deployment.

The Slurm job uses 40×, 512-pixel patches, 384-pixel overlap, HEST segmentation and UNI-v1 features. For multiple slides, every slide completes preprocessing before any inference starts. Per-item states and errors go to `status.json`; the CLI Jobs log includes the Slurm ID, state changes, a tail of Slurm stdout/stderr, and annotation IDs. Canceling a running CLI worker task sends `scancel` on SIGTERM/SIGINT. A hard worker/container kill can leave an orphan Slurm job; operators can use the logged Slurm ID to cancel it manually.

The remote output root is unique for each run, with subdirectories derived from each actual DSA `folderId` and `itemId`: `<remote-output-root>/<run-id>/<folder-id>/<item-id>/trident/40x_512px_384px_overlap/`. This prevents slide-name and retry collisions. Large slides staged temporarily, H5 features, patch coordinates, contours, PNGs and Slurm logs remain on configured HiPerGator project/scratch storage. The worker removes its temporary download directory when it exits. Administrators should set retention on the HiPerGator output root; no automatic deletion is performed. Nothing large is uploaded to Girder/MongoDB.

Each slide's two refined heatmap documents are stored as **native annotations on that slide item**, using the [large image annotation REST API](https://girder.github.io/large_image/annotations.html). An annotation is replaced only when its name, `sourcePlugin` and `sourceItemId` identify this plugin's prior annotation on the same item; unrelated annotations are untouched. Duplicate managed annotations cause an error for manual resolution. A downloadable `<sample>_refined_heatmap.json`, `status.json`, and `manifest.json` are uploaded to a new result item under the slide's actual parent DSA folder's `40x_512px_384px_overlap` subfolder. The manifest records the Slurm job ID, item and checkpoint IDs, SHA-256, parameters and remote paths; it contains no credentials.

## Checkpoint format and verification

`scripts/svc_train_single.py` writes **one** pickle containing `scaler`, `svc` and `metadata`. The metadata contains `class_names=("cortex", "medullary")`, `feature_dimension` and `pca=False`. Labels from the H5 workflow are 0 for cortex and 1 for medullary. Inference uses the binary SVC decision score directly: negative is cortex and zero/positive is medullary. It applies the existing Gaussian refinement, tile coordinates, tissue clipping and DSA JSON export. Independent class models are not combined or assumed calibrated.

Before Athena use, verify the imported XML in HistomicsUI, that selector IDs reach the CLI as expected, worker mount/network access, host key, Slurm account/QOS and L4 GPU, approved checkpoint digest and metadata, one-slide and multi-slide workflows, rendered annotation geometry on the target DSA version, result folder permissions, retry replacement, and cancellation. No local DSA, HiPerGator or GPU run was performed during implementation.
